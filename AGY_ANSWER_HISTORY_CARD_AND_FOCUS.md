# Analysis & Recommendations: History Card Survival & Focus Highlighting

This document provides a comprehensive analysis and architectural review for the two questions raised in `QUESTION_HISTORY_CARD_SURVIVAL_AND_FOCUS_SORT.md`.

---

## Part 1. Question A: History Card Survival (`historyReplay`)

### 1. Evaluation of Fix Direction (Exemption vs Alternative Models)

#### Analysis of Root Cause
In `src/stores/qaStore.ts`, `addReport` supersedes pending cards under the assumption that all cards in `state.cards` originate from previous LLM reports on the target `paragraphId`. When debounced LLM analysis completes and emits `addReport`, any pending card whose exact tuple `(category, originalSegment, suggestedSegment)` is not present in the new LLM payload is dropped:

```ts
// src/stores/qaStore.ts (lines 213-219)
cards: state.cards.filter((card) =>
  !obsoleteCardIds.has(card.id) && (
    card.paragraphId !== payload.paragraphId ||
    card.status !== 'pending' ||
    issueKeys.has(`${card.category}\u0000${card.originalSegment}\u0000${card.suggestedSegment}`)
  )
)
```

This conflates two fundamentally different card lifecycles:
1. **LLM Cards (Report-Bound)**: Transient snapshot generated by non-deterministic background LLM analysis. Superseded when a newer LLM report arrives for that paragraph.
2. **History Replay Cards (Rule/Memory-Bound)**: Deterministic, instant client-side detections derived from user-accepted corrections (`appliedCards`). They remain valid as long as the violation pattern exists in the document text.

#### Verdict on Direction
The user's direction—**exempting `historyReplay` cards from LLM report supersession**—is conceptually and architecturally the correct fix.

#### Refinement on Text Validity Check
A `historyReplay` card should persist through LLM reports, **provided the target text (`originalSegment`) is still present in `payload.paragraphText`**. If the user subsequently edits or deletes the text containing `originalSegment`, the history card should naturally drop or be retired:

```ts
// Recommended filter condition in addReport:
cards: state.cards.filter((card) =>
  !obsoleteCardIds.has(card.id) && (
    card.paragraphId !== payload.paragraphId ||
    card.status !== 'pending' ||
    (card.historyReplay && payload.paragraphText.includes(card.originalSegment)) ||
    issueKeys.has(`${card.category}\u0000${card.originalSegment}\u0000${card.suggestedSegment}`)
  )
)
```

### 2. Coexistence vs Dedup / Fuzzy Merging

#### Coexistence Evaluation
We strongly agree with **NOT introducing fuzzy matching or heuristic deduplication**.

1. **Exact-Tuple Duplication is Already Blocked**:
   In `src/stores/qaStore.ts`, `addCard` already performs an exact tuple check:
   ```ts
   const isDuplicate = state.cards.some(
     (c) =>
       c.paragraphId === newCard.paragraphId &&
       c.category === newCard.category &&
       c.originalSegment === newCard.originalSegment &&
       c.suggestedSegment === newCard.suggestedSegment
   );
   if (isDuplicate) return state;
   ```
   If the LLM independently flags the exact same issue tuple, `addCard` discards the incoming duplicate, keeping the existing `historyReplay` card intact.

2. **Risks of Fuzzy Merging**:
   - As observed in Tasks F, K, and L, broadening match conditions (e.g. matching overlapping substrings, fuzzy category matching, or partial string distance) creates severe false-positive classes.
   - If the LLM produces a garbled rewrite or hallucinates spacing adjustments for a phrase containing the typo, a fuzzy merge would overwrite the user's verified history suggestion with an inferior LLM suggestion.

3. **User Agency and Auto-Cleanup**:
   - If both a history card ("일오일" -> "일요일") and a broader LLM card ("일오일, 월요일" -> "일요일, 월요일") appear, having both visible gives the user full control to pick either.
   - Applying either card mutates the paragraph text in InDesign; upon the next paragraph telemetry event, the unchosen card is automatically detected as stale/obsolete or direct-edited.

### 3. Scope & Regression Check for Question A

#### Scope Assessment: **Small & Well-Contained**
- **Files Touched**:
  1. `src/stores/qaStore.ts`: 1-line update in `addReport` filter condition (`(card.historyReplay && payload.paragraphText.includes(card.originalSegment))`).
  2. `src/stores/__tests__/qaStore.test.ts`: Update test assertions in `qaStore.test.ts` (specifically line 642) to assert that history replay cards persist alongside fresh LLM issues.

#### Interaction Analysis:
- **Task F Direct-Edit Detection**: Direct edits (where `!paragraphText.includes(originalSegment) && paragraphText.includes(suggestedSegment)`) check `directEditCandidates` before the filter. History cards are processed into `newlyObsolete` -> `dismissedCards` with `stale_obsolete` status without regression.
- **Replacement Pipeline & Rollback Guard**: History cards use standard `QACardData` fields (`paragraphId`, `paragraphHash`, `originalSegment`, `suggestedSegment`). Reverse hunk computation in `acceptCard` and rollback verification in `RollbackGuard` work identically.
- **Locate Paragraph**: History cards retain `paragraphId` and `paragraphHash` received from `new-paragraph-detected`, fully compatible with `locateParagraph`.

## Part 2. Question B: Active Paragraph Focus & Card Sorting

### 1. Architectural & UX Review of Focus Highlighting

Connecting the editor's cursor position (`bridgeStore.activeParagraph`) to the corresponding QA card in the dashboard is an excellent UX improvement. However, **how** that connection is presented in the UI requires careful design.

#### Critical UX Pitfalls of Hard Reordering (Array Splicing):
1. **Mis-Click / Focus Stealing Hazard (Fitts' Law Violation)**:
   If a user is about to click "적용" (Apply) on Card B, and a background cursor event or typing trigger causes Card C to splice to the top (index 0), Card B will jump downwards under the mouse pointer. The user may accidentally click the wrong card's action button.
2. **Reading Disorientation & Visual Jitter**:
   During active typing or arrow-key navigation in InDesign, paragraph boundary events fire frequently. If every cursor traversal reorganizes the card list, cards will shuffle constantly, destroying the user's spatial memory.
3. **Loss of Deterministic List Ordering**:
   Mutating the `cards` array order in the store destroys the natural chronological creation order.

---

### 2. Hard Reorder vs. Scroll-into-View + Highlight

| Criteria | Hard Reorder (Move to Top) | Scroll-into-View + Highlight (In-Place) |
| :--- | :--- | :--- |
| **List Stability** | ❌ High jitter, items jump on cursor moves | ✅ Zero jitter, stable card layout |
| **Mis-Click Risk** | ❌ High risk of clicking wrong action button | ✅ Zero risk |
| **Spatial Memory** | ❌ Scrambles user's mental map of cards | ✅ Preserves card position |
| **Visibility** | ✅ Visible at top | ✅ Brought into viewport via smooth scroll |
| **Implementation Complexity** | High (mutates array, handles race conditions) | Low (pure UI presentation & DOM scroll) |

#### Recommendation: **Scroll-into-View + Active Highlight Ring (In-Place)**
- **Visual Highlight**: When `card.paragraphId === activeParagraph?.paragraphId`, `QACardItem` renders an active visual accent (e.g., indigo border ring `ring-2 ring-indigo-500/80 bg-indigo-950/30` and a subtle `"현재 문단"` badge).
- **Smooth Auto-Scroll**: When `activeParagraph` changes, `QACardList` smoothly scrolls the first matching card into view using `scrollIntoView({ behavior: 'smooth', block: 'nearest' })` only if it is outside the visible viewport.

---

### 3. Handling Multiple Cards for the Active Paragraph

#### Analysis:
A single paragraph can produce multiple issues (e.g., spelling error + terminology mismatch, or history card + LLM card).

#### Recommended Strategy:
1. **Group Highlight**: All cards sharing `card.paragraphId === activeParagraph.paragraphId` receive the active focus highlight.
2. **Scroll Target**: The auto-scroll centers on the **first card** in the group (or scrolls just enough to reveal the group using `block: 'nearest'`).
3. **No Arbitrary Heuristic Winner**: Because the bridge telemetry provides paragraph-level boundaries rather than sub-character cursor offsets, attempting to pick a "single most relevant card" via heuristic scoring (e.g. severity or length) would be non-deterministic and prone to ranking errors. Highlighting all cards for that paragraph gives the user a complete, accurate view.

---

### 4. Scope Assessment for Question B

#### Scope: **Small & Self-Contained UI Enhancement**
- **State Plumbing Required**: **None**.
  - `bridgeStore.activeParagraph.paragraphId` is already reactive and broadcast on every `new-paragraph-detected` event.
  - `QACardList.tsx` already consumes `useBridgeStore((s) => s.activeParagraph)`.
- **Target Components**:
  1. `src/components/qa/QACardList.tsx`:
     - Add a `useEffect` keyed on `activeParagraph?.paragraphId` to trigger `element.scrollIntoView({ behavior: 'smooth', block: 'nearest' })` on the matching card ref/element.
  2. `src/components/qa/QACardItem.tsx`:
     - Accept an `isActiveParagraph?: boolean` prop and render an active border/ring accent when `true`.
  3. `src/components/qa/__tests__/QACardList.test.tsx` & `QACardItem.test.tsx`:
     - Add unit tests verifying highlight class presence and scroll invocation.
- **Risk Level**: **Zero risk** to bridge protocol, text diffing, or replacement engine.
